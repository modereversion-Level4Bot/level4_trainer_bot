# Архитектура Level4Trainer

## Общий подход: модульный монолит

`Level4Trainer` строится как **модульный монолит**:
- один Python-сервис для запуска и деплоя;
- четкие границы между модулями по функциональным разделам;
- единые базовые слои `core` и `db`.

Такой подход позволяет развивать проект поэтапно, без хаоса и дублирования.

## Почему нельзя писать все в одном файле

Подход "все в одном файле" делает проект неуправляемым:
- сложно контролировать качество и ошибки;
- почти невозможно быстро найти нужную логику;
- высокая стоимость изменений и сопровождения;
- риски регрессий при любом расширении.

Поэтому код разделяется на самостоятельные модули с понятной ответственностью.

## Принцип clean chat и одно главное UI-сообщение

Основная UX-концепция проекта: **"чистый чат + одно главное окно"**.

Для каждого пользователя в нормальном режиме существует одно актуальное главное сообщение:
- это сообщение представляет текущий экран интерфейса;
- при переходах оно обновляется/заменяется;
- временные медиа-сообщения удаляются, чтобы чат не засорялся (`temporary_messages` для `Questions` audio).

Source of truth для clean-chat контракта:
- runtime-guard в `features/clean_chat/handlers.py` (post-processing delete входящих private user messages);
- helper-контракт в `features/clean_chat/service.py`.

Актуальный контракт clean chat:
- входящее private-сообщение пользователя сначала обрабатывается feature-handler'ами;
- после этого guard делает best-effort удаление сообщения пользователя;
- если удаление не удалось, сценарий не ломается;
- основным интерфейсом остается main UI (`render_main_ui` + one-main-UI-message).

## Слои сообщений

В `core/message_stack.py` заложена модель слоев сообщений:
- `main_ui_message_id` — главное UI-сообщение;
- `ad_message_id` — рекламный слой;
- `announcement_message_ids` — объявления;
- `temporary_media_message_ids` — временные медиа;
- `service_layer_message_ids` — служебные сообщения.

Это позволяет контролировать, что и когда должно оставаться в чате.

## Разделение `handlers` / `service` / `repositories`

- `handlers` — принимают события Telegram и маршрутизируют сценарии;
- `service` — содержит бизнес-оркестрацию (логика сценариев);
- `repositories` — отвечает за работу с SQLite.

Такое разделение снижает связность и делает проект понятным для масштабирования.

## Главное меню v1.0: контекст и условные кнопки

`Main menu` строится из контекста, который собирается в `features/main_menu/service.py`:
- прогресс считается из SQLite (`x из n / x of n`);
- текст меню формируется в `features/main_menu/texts.py`;
- клавиатура формируется в `features/main_menu/keyboards.py`.

Важно:
- строки прогресса отображаются всегда;
- кнопки `📘/🎙` показываются при наличии активного контента;
- кнопка `🛫 Routes` пока скрыта на main menu (TODO endpoint остаётся в handlers);
- справочная кнопка `ℹ️ Как проходит экзамен / ℹ️ How the exam works` показывается всегда;
- `⚙️` показывается всегда и ведет в полноценный модуль `features/settings`;
- строки статуса администратора могут отображаться в тексте главного меню;
- вход в `🛠 Управление / Management` находится в `Settings` и виден только для `ADMIN_IDS`;
- для неготовых разделов используются только `alert/popup` через `safe_answer_callback`, без новых сообщений в чат.

Справочные экраны экзамена вынесены в отдельный модуль `features/exam_info` и также работают через
`render_main_ui` (одно активное главное UI-сообщение).

## Settings v1.0

`Settings` реализованы в отдельном модуле `features/settings`:
- callbacks настроек обрабатываются без отправки лишних сообщений в чат;
- все экраны настроек работают через `render_main_ui`;
- главный экран `Settings` содержит секции `🧭 Main`, `🔔 Notifications`, `👤 Account` (и `🛠 Management` только для admin);
- настройка языка/часового пояса вынесена в подменю `Main`, а звук/совет/напоминания — в подменю `Notifications`;
- `Progress/Restart/Delete account` вынесены в подменю `Account` (удаление скрыто для admin);
- структура раскладки синхронизирована между RU/EN;
- для `ADMIN_IDS` в `Settings` показывается `🛠 Управление`, а кнопка удаления аккаунта в UI скрыта;
- защита от удаления админ-аккаунта сохранена на уровне callback/service;
- message input используется только для `location` и custom `HH:MM`;
- после удаления аккаунта сохраняется минимальная техническая запись в `deleted_account_cleanup` (`telegram_id`, `chat_id`, `message_id`) только для удаления/замены старого main UI на следующем `/start`;
- удаление входящих сообщений остается зоной clean-chat guard.

## Поток данных: Google Sheets -> SQLite

`Google Sheets` рассматривается как источник контента.
Рабочий контур бота — это SQLite.

Цепочка данных:
`Google Sheets -> валидация -> SQLite`

Бот работает с локальной базой SQLite, а не обращается к таблицам напрямую во время общения с пользователем.

Для Questions audio отдельно используется двухшаговый контур:
- source audio path хранится в `questions.audio_file` (Sheets -> SQLite);
- `scripts/preload_question_audio.py` загружает файлы в Telegram service chat (`MEDIA_PRELOAD_CHAT_ID`) и сохраняет `file_id` в `media_assets`;
- runtime в `🎙 Questions` отправляет пользователю audio по `file_id` из `media_assets`;
- если `file_id` не готов, вопрос показывается текстом без user-facing ошибки.

## Safe Telegram utilities

В `core/safe_telegram.py` предусмотрены безопасные обертки для Telegram API:
- `safe_send_message`, `safe_edit_message`, `safe_delete_message`;
- `safe_send_photo`, `safe_send_audio`, `safe_send_voice`;
- `safe_answer_callback`.

Назначение: ошибка при работе с одним пользователем не должна останавливать весь бот.

Важно для UX:
- `toast/notification` через Telegram доступны только для `callback_query` (inline-кнопки);
- для message input-сценариев (`location`, ручной ввод времени) подтверждение отражается переходом на следующий
  экран в основном UI-сообщении, без отдельных сообщений в чат.

## Guard-цепочка

В `core/guards.py` заложен каркас guard-цепочки:
- `update_last_activity`
- `ensure_user_exists`
- `check_admin_block`
- `check_maintenance_mode`
- `check_admin_rights`

Приоритет проверок:
1. Сначала блокировка пользователя.
2. Потом режим техобслуживания.
3. Администраторы продолжают работать даже при техобслуживании.
4. Заблокированный пользователь не получает сообщение о техобслуживании.

## Общие периодические jobs

Фоновые задачи (`jobs/`) построены как общие периодические процессы (JobQueue / APScheduler-compatible):
- `daily_tips_job`
- `reminders_job`
- `ads_job`
- `announcements_job`
- `pending_delivery_job`

Модель "отдельный job на каждого пользователя" не используется.

## Будущая диагностика контента

Диагностика контента запланирована через правила валидации медиа-полей:
- если `*_required = 1`, а путь пустой — это проблема контента;
- если `*_required = 0`, а путь пустой — это допустимо.

Эта логика закладывается заранее для устойчивого импорта из `Google Sheets`.
