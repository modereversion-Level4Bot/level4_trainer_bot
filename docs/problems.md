## P-001

- ID: P-001
- Раздел: Config / DB init
- Суть: `scripts/init_db.py` изначально зависел от `BOT_TOKEN`, потому что путь к базе читался через строгий `get_settings()`.
- Почему важно: Инициализация базы должна работать до настройки Telegram-токена, иначе старт проекта блокируется на подготовительном шаге.
- Варианты решения: (1) Оставить жесткую зависимость и требовать `BOT_TOKEN` заранее, (2) получать `DB_PATH` независимо от `BOT_TOKEN`.
- Рекомендация: Использовать вариант (2) — читать `DB_PATH` напрямую из env/default в слое подключения к базе.
- Решение Константина: Принят вариант (2): в `db/connection.py` путь к базе берется из `DB_PATH`, а проверка `BOT_TOKEN` остается на этапе запуска Telegram-приложения.
- Статус: решено

## P-002

- ID: P-002
- Раздел: Безопасность логирования
- Суть: DEBUG/INFO-логи сторонних библиотек (`telegram.ext`, `httpx`, `httpcore`) показывали полный Telegram Bot API URL с `BOT_TOKEN`.
- Почему важно: Попадание токена в логи создает риск компрометации бота и несанкционированного доступа.
- Варианты решения: (1) Оставить подробные логи и вручную контролировать публикацию, (2) снизить уровень логирования сторонних библиотек и включить маскирование токена.
- Рекомендация: Применить вариант (2): для сторонних логгеров установить уровень `WARNING`, проектные логи оставить на `INFO`, добавить маскирование токена.
- Решение Константина: Уровни логирования для `telegram`, `telegram.ext`, `httpx`, `httpcore`, `apscheduler` снижены до `WARNING`; для проекта сохранен `INFO`; добавлено маскирование токена в логах.
- Статус: решено

## P-003

- ID: P-003
- Раздел: UX / Telegram API ограничения
- Суть: Для событий, приходящих обычным сообщением пользователя (ввод `HH:MM`, отправка геолокации), Telegram не поддерживает показ `alert/popup` как у callback-кнопок.
- Почему важно: В UX-карте предусмотрены предупреждения в формате popup, но технически popup доступен только через `answerCallbackQuery`.
- Варианты решения: (1) перейти на inline-сценарий подтверждения, (2) показывать предупреждение прямо в основном UI-сообщении и/или обычным notification-сообщением.
- Рекомендация: Для onboarding v1 использовать вариант (2), а popup оставлять для действий по inline-кнопкам.
- Решение Константина: Принят вариант (2): для message-based шагов предупреждение выводится в основном UI экране, а для callback-действий используется `alert/toast`.
- Статус: решено

## P-004

- ID: P-004
- Раздел: Clean chat guard / scope
- Суть: Старое описание whitelist-модели clean-chat было не синхронизировано с фактическим runtime.
- Почему важно: Контракт должен быть единым для кода и документации, чтобы не появлялись ложные ожидания по поведению удаления сообщений.
- Варианты решения: (1) вернуть whitelist-механику, (2) зафиксировать фактический runtime-контракт post-processing guard.
- Рекомендация: Использовать вариант (2): считать source of truth runtime-guard в `features/clean_chat/handlers.py` и контракт helper-слоя `features/clean_chat/service.py`.
- Решение Константина: Принят вариант (2): clean-chat работает как best-effort post-processing delete для private user messages, без влияния на message-input flows и one-main-UI.
- Статус: решено

## P-005 — Разделение основных и дополнительных grammar topics

- ID: P-005
- Раздел: Google Sheets / Grammar / Progress model
- Суть: Для MVP нужно явно разделить основные и дополнительные темы грамматики, чтобы прогресс считался только по основным темам.
- Почему важно: Без явного признака тема не может быть корректно отнесена к основному прогрессу (`main`) или дополнительным материалам (`extra`).
- Варианты решения: (1) хранить признак в Google Sheets через `topic_type = main/extra`, (2) дополнительно перенести признак в SQLite на этапе импорта.
- Рекомендация: На этапе импорта добавить поддержку `topic_type` в SQLite (`main` входит в прогресс, `extra` не входит).
- Решение Константина: Реализовано в импорте грамматики: Google Sheets и SQLite используют `topic_type = main/extra`; main-темы входят в основной прогресс, extra-темы не входят.
- Статус: решено

## P-006 — Критерий "завершено" для прогресса

- ID: P-006
- Раздел: Main menu / Progress model
- Суть: В схеме нет единого поля `completed` для всех типов прогресса, поэтому критерии "изучено/пройдено" частично неоднозначны.
- Почему важно: От критериев зависит число `x` в меню и пользовательское восприятие прогресса.
- Варианты решения: (1) зафиксировать единый флаг `is_completed` в таблицах прогресса, (2) оставить текущую схему и явно документировать критерии для каждого раздела.
- Рекомендация: Явно фиксировать критерии по разделам и хранить их в коде/доках:
  - `grammar_progress.status IN ('completed','studied','passed','done','finished')`;
  - `exam_question_progress` (уникальная запись `user_id+level+question_number`);
  - `route_progress.status IN ('completed','done','passed','finished')`.
- Решение Константина: Для Grammar критерий зафиксирован и реализован в training v1.0 — main-тема считается изученной при завершении тренировки с `wrong < total / 2` (excellent/good), extra-темы в основной прогресс не входят. Для Questions критерий реализован через `exam_question_progress` (completed per question). Для Routes критерий остаётся на следующем этапе.
- Статус: частично решено (Grammar + Questions), открыто (Routes)
